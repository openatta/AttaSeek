# 架构设计

> **本阶段目标：** 基于已确认的需求规格，设计软件的骨架结构。只描述"组件做什么、数据怎么流"，不写实现代码。

## 前置条件

- 需求规格文档已就绪（由 `/atta-analyze-requirements` 或 `/atta-feature-dev` 产出）

## 流程

1. **确认输入** — 读取需求规格，理解范围与场景
2. **探索现有模式**（只读） — 查看受影响的现有组件、可复用的模式、项目约定（见 CLAUDE.md）
3. **组件/模块划分** — 每个模块单一职责，标注新建/修改/删除
4. **设计数据流** — 状态存在哪（Jotai atom / 组件本地 / 主进程）、如何传递（props / IPC / context）
5. **定义 IPC 契约**（如涉及） — channel 名、方向、请求/响应类型
6. **技术决策记录** — 每个选择给理由和替代方案

## 铁律

- **不写实现代码** — 类型签名可以写，不给函数体；组件可以写 props 接口，不给 JSX。
- **不写计划** — "先做 A 再做 B"是实现计划的事。架构设计只定义结构，不定义顺序。
- **遵循现有模式** — 不要为了"更好"而偏离项目已有的分层和命名习惯。
- **每个决策有理由** — 不做"显然应该这样"的假设。
