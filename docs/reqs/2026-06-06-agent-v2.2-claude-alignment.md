# Agent Engine V2.2 — Claude Code 对齐需求规格

**目标：** 将对标分析中发现的全部差距转化为可实施的需求，使 AttaSeek Agent Engine 在核心能力上与 Claude Code 对齐，并在多 Agent 场景中构建差异化优势。

**背景：** V2.1 已将总体对齐度从 65% 提升至 78%。本轮将剩余 6 项架构差距 + 工具体系 + MCP + Coordinator + 跨会话 cache + Skills marketplace 全部纳入设计范围，目标对齐度 95%+。

---

## 范围

### In scope（全部 12 项）

**架构增强（4 项）：**

1. **Prompt Cache 共享** — 子 Agent fork/compact/memoryExtract 时共享父 Agent 的系统提示词前缀和工具定义。通过 Anthropic API 的 `cache_control: { type: 'ephemeral' }` 标记断点，使子 Agent 首次 LLM 调用命中 prompt cache。范围限定：同一任务内的父子 Agent 共享，不跨任务持久化。参考 Claude Code 的 `CacheSafeParams` + `SYSTEM_PROMPT_DYNAMIC_BOUNDARY` 模式。

2. **流式工具执行** — LLM 流式响应中，每当收到完整的 `tool_use` 块时立即开始工具执行（而非等待整个响应完成）。读取工具并行执行，写入/风险工具顺序执行。工具结果在下一次 LLM 请求中批量发送。参考 Claude Code 的 `StreamingToolExecutor` + `BatchStream`。

3. **Post-Sampling Hooks 系统** — 在每次 LLM 响应完成后、下一轮开始前执行的钩子管道。支持 confidence rating（置信度评估）、prompt coaching（提示词改进建议）、brief suggestions（简短后续建议）、memory extraction（记忆提取）。钩子可插拔，按 profile 配置触发条件（每 turn / 首次 / 每 N 轮）。参考 Claude Code 的 `stopHooks` 模式：`executePostSamplingHooks()` + `handleStopHooks()`，每个 hook 返回 `{ messages, preventContinuation, blocking }`。

4. **Skills 运行时** — 技能从纯声明式文档升级为具有可执行入口的模块。参考 Claude Code 的文件系统技能模式：每个技能是一个 Markdown 文件（frontmatter 元数据 + Markdown 指令内容），放在 `.claude/skills/` 目录下。技能的 `executionPlan` 由 LLM 根据 skill 的 Markdown 指令动态生成工具调用序列，而非预定义固定步骤。技能注入系统提示词后，LLM 自主决定何时激活技能、调用哪些工具。支持插件提供的技能、MCP 服务器提供的技能。

**工具体系（4 项）：**

5. **工具扩展（高频 12 工具）** — 全面对齐 Claude Code 的工具体系。新增：
   - 文件操作：`write_file`（写入文件）、`edit_file`（精确字符串替换）、`glob`（模式匹配文件搜索）、`grep`（内容搜索）
   - 执行：`bash`（shell 命令，白名单模式：允许非删除、非文件修改、非环境变量修改的命令；30s 超时；支持 `timeout_ms` 参数）
   - 任务管理：`task_create`（创建任务）、`task_update`（更新状态）、`task_list`（列出任务）、`task_output`（获取输出）
   - 通知：`push_notification`（桌面通知）
   - 网络：`web_fetch`（URL 抓取，已有实现待注册）、`web_search`（已有实现待注册）
   - LSP：`lsp_diagnostic`（代码诊断）、`lsp_definition`（跳转定义）、`lsp_references`（查找引用）

6. **工具钩子系统** — 参考 Claude Code 的 `PreToolUse` / `PostToolUse` hooks。每个工具执行前后可注册钩子：pre-hook 可修改输入、阻止执行、注入上下文；post-hook 可修改输出、注入后续消息。Hook 按工具 ID 或通配符匹配注册。

7. **MCP 完整集成** — 支持 MCP (Model Context Protocol) 服务器作为工具和技能的来源。包括：MCP 服务器进程管理（启动/停止/健康检查）、工具发现与注册（`tools/list` → ToolRegistry）、资源访问（`resources/read`）、提示词模板（`prompts/get`）。参考 Claude Code 的 MCP 管理架构（`mcp` 模块中 ~20 文件）。

8. **Skills Marketplace** — 支持从目录/URL 加载第三方技能包。包括：技能包的版本管理、依赖声明、兼容性检查、安装/卸载/更新。技能包可以包含：`SKILL.md`（技能指令）、`tools/`（自定义工具实现）、`prompts/`（提示词模板）、`memory/`（预置记忆）。

**多 Agent 架构（2 项）：**

9. **Coordinator 多 Agent 协调模式** — 参考 Claude Code 的 `coordinatorMode`：一个 Leader Agent 负责任务分解和结果汇总，多个 Worker Agent 并行执行子任务。Leader 维护全局任务列表，将子任务分配给 Worker，收集结果后合成最终输出。Worker 之间不直接通信，通过 Leader 协调。支持 Workflow 脚本编排（`pipeline()` / `parallel()` / `phase()`）。

10. **跨会话 Prompt Cache 持久化** — 将 prompt cache 的共享范围从单任务内扩展到跨会话。对于使用相同 profile 和工具集的连续会话，复用系统提示词和工具定义的缓存。Cache key 基于 `profileId + toolSet + modelId` 的哈希。BrowserWindow 关闭时清理。需要 `CacheManager` 管理 cache 生命周期（创建/命中/失效/清理）。

**隔离与安全（2 项）：**

11. **Worktree 隔离实现** — 实现 `SubAgentContext.isolation: 'worktree'` 模式。子 Agent 在 `git worktree add` 创建的独立工作目录中执行。文件系统变更隔离在 worktree 中。子 Agent 完成后可选择 `merge`（合并变更）或 `discard`（丢弃 worktree）。如果子 Agent 崩溃或被 kill，启动时自动清理残留 worktree。参考 Claude Code 的 `EnterWorktree` / `ExitWorktree` 工具对。

12. **Bash 沙箱与安全策略** — Bash 工具的安全执行环境。白名单策略：默认允许非破坏性命令（读取、搜索、构建、测试），禁止删除文件（`rm`、`rmdir`）、修改关键文件（`/etc/`、`.env`）、修改环境变量、sudo 操作。可配置 `allowUnsafeCommands` 标志（默认 false）。所有命令执行记录到审计日志。

### Out of scope

- 模型训练/微调
- Agent 网络通信/远程执行（本地优先）
- Claude Code 全部 40+ 工具（已选择最高频 12 个 + 保留扩展接口）

### 前置依赖

- Agent Engine V2.1 全部能力（`AgentOrchestrator`、`ToolOrchestrator`、`ContextCompactor`、`MemoryExtractor`、`SubAgentManager`）
- `LLMProvider` 接口已支持 `signal?: AbortSignal`
- `AgentEventBus` 事件系统已就绪
- `src/shared/types/` 类型体系
- `better-sqlite3` 持久化

## 用户场景

### 场景 1: Prompt Cache 共享（同任务内）

- **给定:** 主 Agent 已完成 3 轮对话，系统提示词和工具定义被 Anthropic API 缓存
- **当:** 主 Agent fork 一个 review 子 Agent
- **则:**
  1. 子 Agent 通过 `CacheSafeParams` 复用父 Agent 的 system prompt 前缀（静态部分）和 tools 定义
  2. 静态/动态边界标记为 `SYSTEM_PROMPT_DYNAMIC_BOUNDARY`，cache 断点标记 `cache_control: { type: 'ephemeral' }`
  3. 子 Agent 首次 LLM 调用命中 prompt cache，输入 token 费用为缓存命中价格
  4. 子 Agent 完成后，父 Agent 继续使用自己的 cache 上下文
  5. BrowserWindow 关闭时清理所有缓存

### 场景 2: 流式工具执行

- **给定:** Agent 正在执行编码任务
- **当:** LLM 流式返回 `tool_use(read_file, "src/a.ts")` → 继续生成 → `tool_use(search_code, "function X")`
- **则:**
  1. 收到第一个完整的 `tool_use` 块后，立即开始执行（不等第二个）
  2. 两个读取工具（均为 read risk）并行执行
  3. LLM 响应完全结束后，工具结果已就绪
  4. 工具结果批量注入下轮 LLM 请求

### 场景 3: Post-Sampling Hooks

- **给定:** coding profile 启用了 `confidenceHook`
- **当:** LLM 完成一次响应
- **则:**
  1. Hook 管道按优先级顺序执行：confidence → coaching → brief → memory
  2. Confidence hook 检测模糊信号 → 得分低于阈值 → 生成 coaching message
  3. Brief hook 生成后续建议（"You can ask me to run tests to verify"）
  4. Memory hook 提取关键信息
  5. Hook 结果注入下一轮系统提示词

### 场景 4: Skills 运行时（文件系统技能）

- **给定:** `.claude/skills/code-review/SKILL.md` 定义了审查技能的指令
- **当:** 用户输入 "review my code"
- **则:**
  1. `skillRegistry` 从文件系统加载技能（frontmatter 元数据 + Markdown 指令）
  2. 技能指令注入系统提示词 "## Loaded Skills" 段
  3. LLM 根据技能指令自主决定调用 read_file → search_code → 输出审查报告
  4. 技能执行不依赖预定义的固定步骤 — LLM 根据 context 动态决策

### 场景 5: Bash 工具（安全执行）

- **给定:** Agent 需要运行 `npm test` 验证代码
- **当:** Agent 调用 `bash` 工具，参数 `{ command: "npm test", timeout_ms: 30000 }`
- **则:**
  1. 白名单检查：`npm test` 不是删除/文件修改/环境变量修改命令 → 通过
  2. 在项目工作目录中执行，捕获 stdout/stderr
  3. 超时 30s 后自动 SIGTERM → SIGKILL
  4. 返回 `{ exitCode, stdout: "...", stderr: "..." }`
  5. 如果命令是 `rm -rf /` → 白名单拒绝 → 返回错误

### 场景 6: Worktree 隔离

- **给定:** 用户请求跨 5 个文件的大型重构
- **当:** 主 Agent fork 子 Agent 并指定 `isolation: 'worktree'`
- **则:**
  1. 子 Agent Manager 调用 `git worktree add /tmp/attaseek-worktree-xxx`
  2. 子 Agent 在 worktree 目录中执行所有文件操作
  3. 子 Agent 完成后，通过 `git diff` 生成变更摘要
  4. 主 Agent 选择合并（`git merge`）或丢弃（`git worktree remove`）
  5. 启动时自动清理残留 worktree（`git worktree prune`）

### 场景 7: Coordinator 多 Agent 协调

- **给定:** 用户请求 "全面审计这个项目的安全性"
- **当:** Leader Agent 分析任务，分解为 3 个子任务
- **则:**
  1. Leader 调用 `task_create` × 3，创建子任务（依赖审计、配置审计、代码审计）
  2. Leader fork 3 个 Worker 子 Agent，分配不同 profile（均只读）
  3. Worker 并行执行，结果汇报给 Leader
  4. Leader 调用 `task_output` 收集所有结果
  5. Leader 合成最终审计报告（artifact）

### 场景 8: MCP 工具集成

- **给定:** 用户启动了 filesystem MCP 服务器
- **当:** Agent 需要访问 MCP 提供的 `read_file` 工具
- **则:**
  1. MCP 管理器发现并注册 MCP 服务器的工具到 ToolRegistry
  2. Agent 调用 `read_file` 时，ToolRouter 可能选择 MCP 版本（如更匹配）
  3. ToolExecutor 路由到 MCP 服务器进程执行
  4. 服务器健康检查失败时，自动降级到内置实现

## 风险

- **Prompt cache 实现复杂度** — 需要修改 LLMMessage 类型添加 `cache_control` 字段，修改 AnthropicProvider 在 prompt 中插入断点标记。与现有 PromptTemplate 的 section 系统需要整合（静态/动态边界识别）。
- **流式工具执行并发安全** — AbortController 需要同时取消 LLM 流和正在执行的工具。当前 ToolOrchestrator 的批处理假设是同步等待，需要改为流式异步推送。
- **Bash 工具安全风险** — shell 命令执行是最高风险操作。即使有白名单，LLM 可能通过 prompt injection 尝试绕过。需要严格的命令解析和模式匹配。
- **Worktree 清理风险** — 子 Agent 崩溃或被 kill 导致 worktree 残留。启动清理逻辑需要健壮。
- **Coordinator 的 LLM 成本** — Leader Agent 需要额外的 LLM 调用来分解任务和合成结果，成本倍增。需要预算帽。
- **MCP 集成的稳定性** — MCP 服务器是外部进程，崩溃/超时/协议不兼容都会导致工具调用失败。需要完善的错误处理和降级策略。
- **Skills marketplace 安全** — 第三方技能包可能包含恶意代码。需要沙箱隔离和权限声明机制。
- **跨会话 cache 一致性** — profile 或工具集变更时，缓存需要失效。缓存 key 计算需要包含所有影响 prompt 的因素。
