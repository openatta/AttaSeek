# 软件自动升级 需求规格

**目标：** 为 AttaSeek 桌面端提供端到端自动升级能力——用户无需手动下载安装包即可获得新版本，体验对标 Electron 内置 autoUpdater 与 Chrome 的后台静默升级。
**背景：** AttaSeek 作为桌面应用，当前缺少版本更新机制。用户必须手动检查发布页、下载、安装，流程断裂。升级能力是桌面软件的基线体验，直接影响安全补丁送达率和用户留存。

## 范围

- In scope:
  - **客户端升级引擎**：周期检查、后台下载、完整性校验、安装/替换、重启应用
  - **升级服务端 API**：版本查询接口、二进制包分发接口、渠道管理（stable / beta / nightly）
  - **升级策略配置**：检查频率、下载时机、安装方式（静默 / 提示 / 强制）
  - **升级过程 UX**：通知横幅、下载进度、变更日志展示、安装倒计时/推迟选项
  - **回滚与降级**：升级失败后的自动回退到上一可用版本
  - **平台适配**：macOS（DMG + 签名）、Windows（NSIS/MSI + 签名）、Linux（AppImage / deb）
  - **升级统计**：客户端上报版本分布、升级成功率、失败原因（匿名化，不含用户内容）
- Out of scope:
  - 插件（MCP 子进程）的独立升级（本次只升级 AttaSeek 本体）
  - 系统级包管理器接入（brew / winget / apt 等，后续迭代考虑）
  - 升级 server 自身的用户管理、计费（复用已有基础设施或独立部署）
  - Node.js / Electron 运行时的独立升级（与 AttaSeek 版本绑定，作为一个整体包发布）
- 前置依赖:
  - 代码签名证书（macOS: Developer ID + notarization；Windows: EV Code Signing）
  - 升级服务端的部署基础设施（域名、CDN、存储）
  - 明确的版本号规范（semver，与当前 `package.json` version 对齐）
  - 构建流水线产出各平台安装包并上传至升级服务端

## 用户场景

### 场景 1: 后台自动检查 + 用户确认安装

- 给定: 用户正在使用 AttaSeek v1.2.0（当前渠道 stable），后台有 v1.3.0 可用
- 当: 客户端按周期（默认每 4 小时）向升级服务端发起版本查询
- 则: 
  1. 客户端发现新版本，在窗口内展示非阻断通知横幅（含版本号 + 变更摘要链接）
  2. 用户点击"更新"，客户端开始后台下载安装包（通知区显示进度）
  3. 下载完成后校验签名和哈希，校验通过后提示"就绪——重启以完成更新"
  4. 用户点击"立即重启"，应用正常退出、安装新版本、自动重启
  5. 重启后应用显示"已更新至 v1.3.0"的确认提示

### 场景 2: 静默下载 + 退出时安装（Chrome 风格）

- 给定: 用户正在使用 AttaSeek v1.2.0，后台检测到 v1.3.0
- 当: 用户开启了"自动下载更新"设置（默认开启）
- 则:
  1. 客户端在空闲时自动下载安装包，不打扰用户
  2. 下载完成后仅在校验失败时通知用户
  3. 用户正常退出应用时，安装程序自动执行替换
  4. 下次启动即为新版本

### 场景 3: 强制升级（安全修复）

- 给定: 服务端将 v1.3.0 标记为 `urgency=critical`（例如修复了远程代码执行漏洞）
- 当: 客户端检查更新
- 则:
  1. 通知横幅以更高优先级展示，明确说明"安全更新，建议立即安装"
  2. 下载自动开始，用户不可取消下载
  3. 安装前给予最短倒计时（如 5 分钟），超时后自动重启安装
  4. 用户可选择"推迟"最多 3 次，之后强制安装

### 场景 4: 手动检查更新

- 给定: 用户进入 Settings → General → 点击"检查更新"
- 当: 客户端立即向服务端发起版本查询
- 则:
  1. 有新版本 → 展示版本号、发布日期、变更日志，提供"下载并安装"按钮
  2. 已是最新 → 展示"AttaSeek 已是最新版本（v1.2.0）"
  3. 网络不可达 → 展示"无法连接更新服务器，请检查网络"（含重试按钮）
  4. 服务端错误 → 展示"更新服务暂时不可用，请稍后重试"

### 场景 5: 下载中断续传

- 给定: 用户已开始下载 v1.3.0 安装包（总共 120MB），下载至 60MB 时网络断开
- 当: 网络恢复后
- 则: 客户端从断点继续下载（HTTP Range 请求），而非从头开始；进度条从 50% 继续

### 场景 6: 安装校验失败

- 给定: 客户端已下载完安装包
- 当: 签名验证或 SHA256 哈希校验失败
- 则:
  1. 删除已下载的损坏文件
  2. 通知用户"更新包校验失败，将重新下载"（或提供手动重试）
  3. 自动重新发起下载（最多重试 2 次）
  4. 若 3 次均失败，通知用户并建议稍后手动检查

### 场景 7: 版本回滚

- 给定: 用户升级到 v1.3.0 后，应用频繁崩溃
- 当: 应用检测到连续启动失败（3 次 / 5 分钟内）
- 则:
  1. 自动回退到上次已知良好的版本（v1.2.0），备份在安装目录的 `versions/` 下
  2. 提示用户"检测到新版本不稳定，已自动恢复到 v1.2.0"
  3. 将该设备标记为"跳过该版本"，不再自动推送 v1.3.0

### 场景 8: 下载带宽控制

- 给定: 用户正在使用移动热点，带宽有限
- 当: 客户端检测到按流量计费的网络（Windows / macOS 可检测）
- 则:
  1. 不自动下载，改为提示"检测到按流量计费的网络，有新版本可用，是否下载？"
  2. 用户确认后才开始下载
  3. 下载时限制速率（默认不占满带宽，可配置）

### 场景 9: 多实例协调

- 给定: 用户同时打开了两个 AttaSeek 窗口（多窗口模式）
- 当: 某一窗口触发更新安装
- 则:
  1. 更新协调以进程级单例执行（只下载一次）
  2. 所有窗口展示相同的更新进度通知
  3. 重启时所有窗口关闭，安装完成后恢复会话（可选）

## 升级服务端需求

### 版本查询接口

- 客户端提供：当前版本（semver）、平台（`darwin-x64` / `win32-x64` / `linux-x64` 等）、渠道（`stable` / `beta` / `nightly`）、架构
- 服务端返回：最新版本号、发布日期、变更日志 URL、安装包下载 URL、包大小（bytes）、SHA256 哈希、urgency 级别（`latest` / `recommended` / `critical`）、最小可直升级版本（低于此版本的必须先升到中间版本）

### 二进制包分发

- 安装包通过 CDN 分发，支持 HTTP Range 请求（断点续传）
- 服务端提供重定向或直接下载 URL
- 可选：对低频升级路径做 delta 差分包（v1.0 → v1.5 跨多个版本）

### 渠道管理

- 服务端支持多发布渠道：`stable`（默认）、`beta`（预览功能）、`nightly`（开发主线）
- 客户端在设置中选择渠道，持久化到本地
- 不同渠道的版本号独立演进

### 升级统计与监控

- 客户端在升级事件发生时匿名上报：事件类型（`check` / `download_start` / `download_complete` / `install_start` / `install_success` / `install_fail` / `rollback`）、当前版本、目标版本、平台、失败原因码
- 服务端聚合统计各版本分布、升级成功率、失败原因分布
- 上报不含任何用户身份信息或业务内容

## 非功能需求

- **可靠性**：升级本身不能成为故障源。校验失败必须拒绝安装；回滚必须可用。
- **安全性**：安装包必须通过代码签名验证 + 哈希校验双重验证。升级服务端通信必须走 HTTPS。
- **性能**：后台检查对应用性能无感知影响（不阻塞 UI 线程）。下载使用空闲带宽。
- **兼容性**：升级不得破坏用户本地数据（会话记录、设置、插件配置）。用户数据目录与安装目录分离。
- **离线友好**：网络不可达时优雅降级，不弹错误对话框。

## 待澄清（已全部确认）

- [x] **更新服务端归属**：双源策略 —— 优先查 GitHub Releases，无结果则回退到 AttaCloud 升级接口。
- [x] **Delta 差分更新**：类似 VS Code 方案（全量下载 + Squirrel/NSIS 平台原生安装器）。
- [x] **代码签名自动化**：当前暂无签名证书，先按有签名的架构设计（验证步骤留位），后续接入真实签名。
- [x] **版本强制回滚策略**：不需要服务端撤回版本。客户端本地保留回滚能力即可。
- [x] **企业/团队部署**：不需要自定义服务器。局域网场景用户手工下载安装包。
- [x] **首次启动行为**：静默检查更新，不弹窗打扰。

## 风险

- **签名证书风险**：若代码签名证书过期或被吊销，升级包将无法通过验证，导致所有用户无法自动升级——需要证书到期监控和提前续期流程。
- **CDN 成本风险**：若每个版本完整包 150MB+，月活用户 10K+，带宽成本可能显著。需评估是否需要差分更新或 P2P 分发。
- **升级破坏用户数据风险**：若新版本修改了数据格式（SQLite schema 变更等），老版本回滚后可能无法读取已迁移的数据。升级前必须做数据向后兼容性检查。
- **强制升级用户反感风险**：安全级别的强制升级虽然必要，但可能打断用户工作流。需权衡 urgency 分级粒度和推迟次数上限。
- **版本碎片化风险**：多渠道（stable / beta / nightly）若缺乏明确的升级路径，可能导致用户困在某个渠道无法平滑迁移到另一渠道。
