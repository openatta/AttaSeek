# 借鉴 Claude Code 改进 AttaSeek Agent — 分析与实施简报

> 阶段 1：分析与设计（只读）
> 基于 `docs/analysis/claude-code-vs-attaseek-agent.md` 中识别的可借鉴方向

## 一、范围定义

### In（本次分析覆盖的 6 个方向）

| # | 方向 | 一句话目标 |
|---|------|-----------|
| 1 | **内存系统增强** | 引入会话内存层 + LLM 驱动的关联选择 |
| 2 | **钩子系统扩展** | 增加 PermissionRequest、SubagentStart/Stop、Elicitation 事件 |
| 3 | **工具摘要升级** | 从启发式规则升级为小模型 LLM 生成 |
| 4 | **MCP 传输增强** | 增加 HTTP/WS 传输 + OAuth 授权流程 |
| 5 | **Token 估算升级** | 从字符估算升级为 API + 回退链 + 文件类型感知 |
| 6 | **遥测升级** | 考虑引入 OpenTelemetry 分布式追踪 |

### Out（不在本次范围）

- 不改 AttaSeek 以外的代码
- 不引入新的外部依赖框架（OTel SDK 除外）
- 不重构现有模块的核心架构
- 不改变 AgentProfile / QueryLoop 的对外接口

## 二、逐方向场景分析

### 方向 1: 内存系统增强

**现状**：
- `FileMemory.ts`：加载 CLAUDE.md + `.atta/seek/memories/*.md`（L0）
- `MemdirManager.ts`：解析 MEMORY.md 索引 + 加载条目文件
- `MemoryExtractor.ts`：对话结束后 LLM 提取（fire-and-forget），带游标+合并
- **缺失**：无**会话级**自动维护的内存层（对应 Claude Code 的 SessionMemory）

**Claude Code 做法**：
- 三层：文件内存（memdir）→ 会话内存（SessionMemory，后台子代理定期更新）→ 持久提取（extractMemories）
- 关联选择：`findRelevantMemories()` 使用 Sonnet 查询，选最多 5 个相关记忆

**改进方案**：

**1a. 会话内存层（SessionMemory）**

新增 `src/main/agent/memory/SessionMemory.ts`，提供：
- `updateSessionMemory(sessionId, messages, goal)` — 用 compact 模型定期生成会话摘要
- `getSessionMemory(sessionId)` — 读取当前会话的内存文件
- 触发条件：turnCount 达到配置阈值（默认每 5 轮）
- 存储位置：`~/.atta/seek/sessions/{sessionId}/session-memory.md`
- 注入方式：在 `prompt/sections/memory-context.ts` 渲染时追加会话内存节

**1b. LLM 关联选择（LLM-powered relevance）**

升级 `MemdirManager.ts`，新增：
- `findRelevantMemories(query, allMemories)` — 用 small_fast 模型排序记忆相关性
- Prompt 模板：给定当前 goal + 最后几条消息，从 N 条记忆中选出最相关的 K 条（≤5）
- 缓存：同一 queryChainId 内不重复查询

**数据流**：
```
FileMemory (L0) ──┐
MemdirManager ────┤
                  ├──→ ContextAssembler.assemble() → 注入系统提示
SessionMemory ────┤
LLM Relevance ────┘
```

**关键决策**：
- 会话内存使用 compact 模型（低成本），关联选择使用 small_fast 模型
- 会话内存为**增量更新**（只追加新信息，不重写全量），减少 LLM 调用开销
- 关联选择缓存 在 queryChainId 粒度，同一次执行不重复查询

### 方向 2: 钩子系统扩展

**现状**：`HookTypes.ts` 定义 9 种事件类型，但缺少 3 个重要事件：
- `PermissionRequest` — 工具权限请求时触发
- `SubagentStart` / `SubagentStop` — 子代理生命周期
- `Elicitation` — 用户追问/澄清时触发

**Claude Code 做法**：25+ 事件类型，覆盖完整生命周期。`PermissionRequest` 钩子可覆盖权限决策。

**改进方案**：

**2a. 增加事件类型**

在 `HookTypes.ts` 中扩展 `HookEventType` 联合类型：
```typescript
export type HookEventType =
  | /* existing 9 types */
  | 'PermissionRequest'   // 工具权限请求（可覆盖决策）
  | 'SubagentStart'       // 子代理开始执行
  | 'SubagentStop'        // 子代理执行完成
  | 'Elicitation'         // 用户追问/澄清
```

**2b. 扩展 HookContext**

新增字段：
```typescript
export interface HookContext {
  // ... existing fields
  // PermissionRequest 专用:
  permissionToolName?: string
  permissionToolInput?: unknown
  permissionDecision?: 'allow' | 'deny' | 'ask'
  // SubagentStart/Stop 专用:
  subagentId?: string
  subagentProfile?: string
  subagentResult?: string
  // Elicitation 专用:
  elicitationQuestion?: string
  elicitationResponse?: string
}
```

**2c. HookResult 扩展**

新增 `permissionDecision` 覆盖字段：
```typescript
export interface HookResult {
  // ... existing fields
  /** PermissionRequest hooks can override the decision */
  permissionDecision?: 'allow' | 'deny' | 'ask'
}
```

**2d. 触发点**

| 事件 | 触发位置 | 文件 |
|------|---------|------|
| `PermissionRequest` | `ToolExecutor.ts` 中 `checkPermission()` 之前 | `src/main/tools/ToolExecutor.ts` |
| `SubagentStart` | `SubAgentManager.fork()` 创建子代理后 | `src/main/agent/subagent/SubAgentManager.ts` |
| `SubagentStop` | 子代理 queryLoop 完成后 | 同上 |
| `Elicitation` | `AskUserQuestion` 工具执行时 | `tools/implementations/question-impl.ts` |

**关键决策**：
- `PermissionRequest` 钩子的 `permissionDecision` 优先级**低于**用户显式设置的权限规则（白名单 > 钩子 > 默认）
- 钩子执行失败不影响主流程（现有模式不变）
- 不创建新的钩子执行器类型，复用现有的 command/prompt/http/callback

### 方向 3: 工具摘要升级

**现状**：`tool-summary.ts` 使用纯启发式规则。`generateToolUseSummary()` 按工具类型硬编码摘要逻辑。`generateLLMToolUseSummary()` 已声明但 `throw new Error('not yet wired')`。

**Claude Code 做法**：使用 Haiku 模型并行生成工具使用摘要，每个工具结果独立摘要后合并。

**改进方案**：

**3a. 实现 `generateLLMToolUseSummary()`**

替换占位实现，使用 small_fast 模型：
- **输入**：`ToolUseSummaryEntry` 的简单版（toolName + truncatedContent）
- **Prompt**：`"You are a tool output summarizer. For each tool call below, produce a one-line action summary and a one-line result summary."`
- **输出**：结构化 JSON → 解析为 `ToolUseSummaryEntry[]`
- **预算**：单次最多 10 个工具调用，超过则分批
- **超时**：5 秒（摘要不需要精确），超时回退到启发式

**3b. 在 query-loop 中升级消费**

`query-loop.ts` 第 921-943 行：将 `generateToolUseSummary()` 替换为：
```typescript
const summary = toolUses.length <= 2
  ? generateToolUseSummary(...)           // 少数工具：启发式足够
  : await generateLLMToolUseSummary(...) // 多数工具：LLM 更准确
```

**3c. 并行优化**

工具摘要生成**不阻塞**下一个 LLM 调用的系统提示组装——在工具执行期间异步启动，等待结果后再决定是否注入。

**关键决策**：
- 混合策略：≤2 个工具用启发式（更快），>2 个用 LLM（收益更高）
- 使用 `small_fast` 模型（低成本），超时回退到启发式
- 摘要结果缓存到会话级（同一 sessionId 的同一 tool_call_id 不重复生成）

### 方向 4: MCP 传输增强

**现状**：
- `MCPTransport.ts`：支持 stdio（完整实现）+ sse（标记为 stub）
- `MCPConfigLoader.ts`：仅解析 `stdio` / `sse` 两种类型
- **缺失**：HTTP 传输、WebSocket 传输、OAuth 授权

**Claude Code 做法**：6 种传输（stdio, sse, sse-ide, http, ws, sdk）+ 完整 OAuth 2.0 流程（`auth.ts` 88KB）

**改进方案**：

**4a. HTTP 传输实现**

在 `MCPTransport.ts` 中新增 `HttpTransport` 类：
- `connect()` — 验证端点可达（HEAD 或 GET /health）
- `send(message)` — POST JSON-RPC 到配置的 URL
- `onMessage(handler)` — 通过轮询或 SSE 子通道接收通知
- 复用现有 `fetch` API（无额外依赖）

**4b. WebSocket 传输实现**

新增 `WSTransport` 类：
- `connect()` — `new WebSocket(url)` + 等待 open 事件
- `send(message)` — `ws.send(JSON.stringify(message))`
- `onMessage(handler)` — `ws.on('message', data => handler(JSON.parse(data)))`
- `disconnect()` — `ws.close()`
- 自动重连：断开后指数退避重连（1s/2s/4s/8s，最多 5 次）
- Node.js 环境用 `ws` 包（项目中可能已有），浏览器环境用原生 WebSocket

**4c. MCPConfigLoader 扩展**

`parseTransportConfig()` 中新增对 `http` 和 `ws` 的解析：
```typescript
case 'http': return { type: 'http', url: raw.url, headers: raw.headers }
case 'ws':   return { type: 'ws',   url: raw.url, headers: raw.headers }
```

**4d. OAuth 授权流程（轻量版）**

新增 `src/main/agent/mcp/MCPOAuth.ts`：
- 支持 OAuth 2.0 Authorization Code Grant
- `startAuth(serverConfig)` — 打开浏览器到授权 URL → 本地 HTTP 服务器接收回调 → 交换 code 为 token
- `refreshToken(serverConfig)` — 用 refresh_token 刷新 access_token
- Token 持久化：存储在 `~/.atta/seek/mcp-tokens.json`（加密可选）
- 范围：仅支持最常用的 Authorization Code Grant，不支持 Device Code / Client Credentials

**关键决策**：
- MCP HTTP/WS 传输为**渐进增强**——现有 stdio 行为不变
- OAuth 为简化版（~300 行）而非 Claude Code 的 88KB 完整实现
- WS 重连逻辑复用于 SSE 传输的重连
- `MCPTransport` 接口不变——新传输只增加实现类

### 方向 5: Token 估算升级

**现状**：`compact/token-counter.ts` 仅使用 `Math.ceil(chars / 4)`，无文件类型感知，无 API 回退链。

**Claude Code 做法**：三层回退（API count_tokens → Haiku 回退 → 字符估算），文件类型感知（JSON 2 bytes/token），图像/文档块 2000 tokens 静态估算。

**改进方案**：

**5a. 增加 API 计数的首选项**

在 `token-counter.ts` 中新增：
```typescript
export async function estimateTokensAccurate(
  messages: LLMMessage[],
  model: string,
  systemPrompt: string,
  tools: LLMToolDef[],
): Promise<number> {
  // 1. 尝试 Anthropic count_tokens API（如果 provider 支持）
  // 2. 尝试 OpenAI compatible /v1/tokenize（如果 provider 支持）
  // 3. 回退到 estimateTokens(text) 字符估算
}
```

**5b. 文件类型感知估算**

```typescript
export function estimateTokensByType(text: string, filePath?: string): number {
  const bytesPerToken = getBytesPerToken(filePath)
  return Math.ceil(text.length / bytesPerToken)
}

function getBytesPerToken(filePath?: string): number {
  if (!filePath) return 4
  const ext = path.extname(filePath).toLowerCase()
  if (['.json', '.jsonc', '.jsonl'].includes(ext)) return 2    // JSON dense
  if (['.yaml', '.yml', '.toml', '.ini'].includes(ext)) return 3  // config dense
  if (['.md', '.txt', '.csv'].includes(ext)) return 4           // prose
  return 4  // default
}
```

**5c. 回退链集成位置**

在 `query-loop.ts` 的压缩管道（步骤 5）中，用 `estimateTokensAccurate()` 替换 `estimateMessagesTokens()`：
- **预算检查**：使用字符估算（需快速，不阻塞循环）
- **压缩决策**：使用 API 计数（更准确，避免过早/过晚压缩）
- **异步启动**：在 LLM 调用期间并行进行 token 计数，结果在下一轮决策中使用

**关键决策**：
- 字符估算保留为**默认 + 回退**，不删除（无需网络、即时）
- API 计数用于压缩阈值判断（精度更重要），预算检查用字符估算（速度更重要）
- 文件类型感知仅扩展 `estimateTokensByType`，不改变现有签名
- 不引入 `tiktoken` 依赖（太重，且 Claude 模型 tokenizer 不公开）

### 方向 6: 遥测升级（非紧急）

**现状**：`TelemetryService.ts` 自建 JSONL 文件存储，18 种事件类型，无分布式追踪，无采样。

**Claude Code 做法**：OpenTelemetry 全栈（Meter + Logger + Tracer），多导出器（gRPC/HTTP/Prometheus/Console），BigQuery 指标导出，Perfetto 追踪，PII 保护。

**改进方案**：

**6a. 分阶段路径**

| 阶段 | 内容 | 优先级 |
|------|------|--------|
| Phase 1 | 保持 JSONL，增加更多事件覆盖（SubagentStart/Stop, PermissionRequest） | 低 |
| Phase 2 | 引入 OTel SDK（可选依赖），增加 Span 追踪（交互→LLM→工具） | 低 |
| Phase 3 | 多导出器支持 + 采样 | 低 |

**6b. 最小化当前改进**

当前只需：
- 在现有 `TelemetryService` 中新增 3 个事件类型（对应钩子扩展）
- `agent_subagent_started` / `agent_subagent_completed` / `agent_permission_requested`
- 保持 JSONL 存储模式，不引入 OTel 依赖

**关键决策**：
- **不引入 OTel SDK** 作为默认依赖（增加 ~500KB 包体积）
- OTel 支持作为可选特性（`ATTA_OTEL_ENDPOINT` 环境变量驱动）
- 当前 JSONL 遥测已满足内部调试需求，OTel 在需要生产监控时再实施

## 三、实施路径（粗粒度 Task 列表）

按**收益/成本比**和**依赖关系**排序：

```
T1  ──→ T3  ──→ T2  ──→ T4  ──→ T5
 │                              │
 └── 无依赖，可并行              └── T1 完成后可开始

T6 独立，非紧急，可随时插入
```

| Task | 方向 | 描述 | 预估改动文件数 | 难度 |
|------|------|------|--------------|------|
| **T1** | 内存增强 | 会话内存层 + LLM 关联选择 | 4-5 个文件 | 中 |
| **T2** | 钩子扩展 | 4 个新事件类型 + 触发点 | 6-8 个文件 | 低 |
| **T3** | 工具摘要升级 | 实现 LLM 摘要 + 混合策略 | 2-3 个文件 | 低 |
| **T4** | MCP 增强 | HTTP/WS 传输 + OAuth | 4-5 个文件 | 中 |
| **T5** | Token 估算升级 | API 计数 + 文件类型感知 | 2-3 个文件 | 中 |
| **T6** | 遥测升级 | 新增事件类型（JSONL 扩展） | 1-2 个文件 | 低 |

**推荐执行顺序**：T2 → T3 → T1 → T4 → T5 → T6

理由：T2（钩子）最简单，改动面小，且为后续的内存/工具摘要提供事件基础。T3（工具摘要）已有占位函数，只需实现。T1（会话内存）依赖 T2 的 SubagentStop 事件来触发后台摘要。T4 和 T5 独立性高，可并行。T6 非紧急。

## 四、风险

| 风险 | 影响方向 | 缓解 |
|------|---------|------|
| LLM 摘要（T1/T3）增加 API 调用成本 | T1, T3 | 使用 small_fast/compact 模型；设置严格超时；混合策略保守触发 |
| 会话内存文件可能膨胀 | T1 | 限制文件大小（50KB）；增量更新而非全量重写 |
| OAuth 实现的安全风险 | T4 | 仅支持 Authorization Code Grant；HTTPS 强制；token 加密存储 |
| API token 计数增加延迟 | T5 | 并行异步执行；仅压缩决策使用；预算检查保留字符估算 |
| 钩子扩展可能破坏现有钩子行为 | T2 | 新事件类型为纯增量；不改现有 HookEventType 语义 |
